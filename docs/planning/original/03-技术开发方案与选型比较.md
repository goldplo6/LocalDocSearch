# LocalDocSearch｜技术开发方案与选型比较

> 版本：讨论草案 v0.1｜2026-11-06  
> 当前目标：Windows 11 独立桌面软件，完全开源，默认离线  
> 重要声明：**以下为候选与推荐路线，不表示技术栈已经确定。** 文中列出的第三方库均需在实际引入时再次核对适配版本与依赖许可证。

> 关联：[开发阶段与预期成果](01-开发阶段与预期成果.md) · [软件需求规格说明书](02-软件需求规格说明书.md)

## 0. 先给结论

- **目前推荐路线 A**：**C# + .NET 10 + WPF + Open XML SDK /（按情况）ClosedXML + PdfPig + 流式文本/CSV 提取 + 直接扫描搜索**；Office COM 仅用于**可选的精准打开定位**。阶段 4 测试后，再决定要不要加入 SQLite 提取缓存或专门全文索引。
- **值得认真对比的路线 B**：**C# + .NET 10 + Avalonia**，正文解析与搜索层沿用路线 A；它为未来 macOS/Linux 留路，但 Windows 特有 Office 操作仍需平台模块。
- **不要在 v1.0 把正则、FTS、OCR、跨平台同时拉入主线**。第一版的关键指标不是“用了高级搜索引擎”，而是用户能不能搜到全部应有结果，并准确识别对应文件和上下文。
- **AND/OR 用独立的两个按钮 / 切换控件**，与“正则表达式”完全正交。AND/OR 在文件级组合关键词；正则若未来添加，应成为单独的高级查询模式，且须限制复杂表达式的运行时间。

## 1. 评价标准

各路线按以下因素评估（不是未经实测的量化评分）：

1. Windows 11 的桌面体验（文件选择、资源管理器、Office 自动化、高 DPI、键盘操作）。
2. 多格式正文解析可用的成熟库，以及中文和文档位置映射的可控程度。
3. 大量文件/大文件处理时的性能、内存、取消和错误隔离能力。
4. 对个人开发者与 AI 辅助编程的复杂度、测试可维护性。
5. 未来开源贡献者的可参与性、依赖许可证和构建发布成本。
6. 未来可能跨平台的迁移代价（但**不为了尚未发生的需求牺牲第一版稳定性**）。

## 2. 桌面框架对比（这是第一个待决定项）

| 方案 | 优点 | 缺点与风险 | 何时选择 |
|---|---|---|---|
| **C# / .NET 10 / WPF** | 成熟 Windows 桌面模型，MVVM 和数据绑定生态稳定；和 Win32、资源管理器、COM/Office 集成顺畅；适合高信息密度列表 | 只支持 Windows；若将来跨平台，UI 基本需要重写（核心库可保留） | **当前首选：第一版只做 Win11、重视 Office 定位** |
| **C# / .NET 10 / Avalonia** | C# + XAML 风格；Windows/macOS/Linux 共用大量 UI 代码；MIT 许可的核心框架 | 某些复杂控件、Windows 原生行为与 WPF 不同；Office COM 仍仅 Windows；需验证中文输入、列表虚拟化和辅助功能 | 未来跨平台概率高，愿为此接受前期 UI 验证投入 |
| **C# / .NET / WinUI 3** | 微软面向新 Windows App 推荐的原生 UI 方向，Fluent 风格自然；现代窗口特性好 | Windows App SDK 部署、版本与生命周期的细节较多；数据网格、桌面经典场景需核实组件生态 | Windows 11 风格优先、愿投入打包与控件验证 |
| **Python / PySide6** | 文本和文档处理库多；原型迭代快；Qt 控件成熟 | 发行包大小与运行环境管理需处理；大量文件扫描要特别避免 GUI 线程卡顿；PySide6 的 LGPL/GPL/商业许可需要认真合规 | 开发团队 Python 熟悉度明显高于 C#，主要想快速验证产品 |
| **Rust / Tauri 2 + Web 前端** | 较灵活的 UI 设计，Rust 适合性能敏感的本地工作；跨平台，Windows 使用 WebView2 | 两套技术语言/工具链、Rust 编译和 Office COM 对接成本；文档解析要评估 crate 成熟度或额外 sidecar | 未来多平台和 Web UI 是强目标，团队熟 Rust/前端 |
| **TypeScript / Electron** | 前端生态大、复杂界面开发快，跨平台；社区资料丰富 | 打包体积和内存通常较高；原生 Office 定位和解析器可能需要原生模块或独立进程 | 团队极擅长 Web 前端，UI 复杂度超过原生集成要求 |

**我的判断**：开发者已经装 Office、当前只需 Win11；WPF 更有利于把“搜索 → Office 定位”尽快做通。真正担心将来跨平台时，**C# + Avalonia** 是最自然的替代，不必为跨平台立刻换成 Rust/Tauri。WPF 和 Avalonia 都可能满足产品需求；应做**同一数据集的 UI 原型对比**后确认。

### 2.1 待验证的 WPF vs Avalonia 小实验

同一个测试窗口实现：目录选择、关键词标签、AND/OR、文件类型多选、10000 条虚拟化结果、上下文高亮、展开折叠、取消搜索、Win11 缩放（100/150/200%）、中文输入法。评估开发工时、界面流畅度、内存、高 DPI 和构建安装。**选框架前先完成这个实验，比仅凭风格偏好更稳妥。**

## 3. 程序架构：保持 UI/搜索/文件格式/定位解耦

```text
┌──────────────────────────────────────────────────────┐
│ Desktop UI：WPF / Avalonia / WinUI（最终三选一）        │
│ MainViewModel · SettingsViewModel · ResultViewModel  │
└──────────────────────┬───────────────────────────────┘
                       │ SearchRequest / CancellationToken
┌──────────────────────▼───────────────────────────────┐
│ Application / UseCases                               │
│ ScanFolder → ExtractSegments → MatchTerms            │
│ → GroupResults → StreamResults → OpenOrLocate        │
└──────────────┬─────────────────┬─────────────────────┘
               │                 │
    ┌──────────▼──────────┐ ┌────▼──────────────────────┐
    │ Extraction Adapters │ │ Locator Adapters          │
    │ Text/CSV/Word/      │ │ Text editor / Office COM  │
    │ Excel/PPT/PDF       │ │ PDF viewer / Shell fallback│
    └──────────┬──────────┘ └───────────────────────────┘
               │
    ┌──────────▼──────────────────────────────────────┐
    │ Optional Cache / Index Provider（后续可插拔）     │
    └─────────────────────────────────────────────────┘
```

关键接口（概念性伪代码，不限制最终具体 API）：

```csharp
interface ITextExtractor
{
    bool CanRead(string extension);
    IAsyncEnumerable<TextSegment> ExtractAsync(
        string path, ExtractionOptions options, CancellationToken ct);
}

record TextSegment(
    string Text,
    SourceLocator Locator,
    string SegmentId);

interface ISearchEngine
{
    IAsyncEnumerable<SearchEvent> SearchAsync(
        SearchRequest request, CancellationToken ct);
}

interface IMatchLocator
{
    bool CanLocate(SourceLocator locator);
    Task<LocateResult> OpenAndLocateAsync(
        string filePath, SourceLocator locator, CancellationToken ct);
}
```

**重要设计细节**：不能先把全文强行拼成一个没有位置信息的大字符串再查找。提取器应按“可定位单元”生成段：Word 段落/表格单元，Excel 单元格，PPT 幻灯片对象，PDF 页内文本块，纯文本行或适当大小的连续流式块。若按块切分，必须处理**关键词跨块边界**（保留尾部重叠区或状态机），并将字符偏移正确映射回原文件。

### 3.1 文件读取和定位不使用同一个依赖

- **正文读取**：Open XML 等不需要 Office 安装的库，读取磁盘上文件，绝不启动 Office 执行文件中的宏。
- **打开定位**：仅当用户双击并显式要求操作时调用 Word/Excel/PowerPoint 桌面程序（如可用），以 COM 做最佳努力定位。
- **公开版回退**：无 Office 或 COM 失败时，使用系统默认关联程序打开，并展示工作表+单元格、幻灯片、段落等位置信息。

这样可以降低兼容性风险，同时保持公开版“没有 Office 仍可搜索”的核心承诺。

## 4. 文件内容提取库的可选路线

| 格式 | 候选技术 | 优点 | 代价 / 限制 | 初步建议 |
|---|---|---|---|---|
| TXT/MD/LOG | .NET 流式读取 `StreamReader` + 编码策略 | 无重型依赖、可控内存、利于行号 | GB18030/混合编码、截断和跨块匹配需自己处理 | **首选** |
| CSV | 轻量自研状态机或成熟 CSV 解析库（引入前查许可证） | 能处理双引号、分隔符、字段跨行 | 逻辑行 ≠ 物理行；格式方言有差异 | **格式正确性优先**，先评估成熟库 |
| DOCX/PPTX | Microsoft Open XML SDK | 官方 OpenXML 生态、无需 Office、MIT | 需理解文档部件和 XML 结构；“视觉页码”难获得 | **首选** |
| XLSX | Open XML SDK 流式读取 | 大文件时内存可控；工作表/单元格位置天然存在 | 共享字符串、日期/样式/公式缓存解析更繁琐 | **默认优先**，大文件友好 |
| XLSX | ClosedXML | 对 Excel 单元格操作更直观、API 好用、MIT | 大工作簿可能产生更高内存开销；完整“显示值”仍有复杂性 | **原型候选**，与 OpenXML 做压力对比 |
| PDF | PdfPig | 能读取页面文字和部分位置布局数据；Apache-2.0 | 多栏顺序、字体编码、扫描件和加密文件难处理 | **首选试验**，页码是基础定位 |
| Office 文档转纯文本 | 使用已安装 Office 自动化读取 | 对某些边缘内容可能更接近 Office 视图 | 强制依赖 Office、启动慢、COM/安全策略复杂 | **不用于默认正文读取**；仅定位 |

### 4.1 Excel 的三个“值”，必须分清

同一个单元格可能有：`原始存储值`、`公式文本`、`公式缓存的计算结果/显示内容`。样式还可能把数值显示成不同的日期、百分比或金额。第一版需要在文档与 UI 中说明采用哪种值来搜索，不应未经验证就承诺与 Excel 界面看到的文字 100% 相同。建议先保证**原始文本值 + 明确的公式搜索选项**，并在阶段 0 验证如何读取缓存显示值。不要因为读取 XLSX 就自动打开 Excel 进行重算。

### 4.2 Word/PPT 中的“完整内容”并非一项简单开关

文本框、批注、页眉页脚、备注页、图形中的文字可能在不同文档部件中；默认先支持可靠的正文/表格，逐项加入提取器并做可重复样本。设置页面只暴露真正实现且通过测试的选项。

### 4.3 编码与异常读取

- TXT/MD/LOG：识别 BOM、优先 UTF-8；GB18030 等编码可选回退或经过质量校验再自动尝试；记录采用的编码和替代字符警告。
- CSV：支持 RFC 4180 类常见引号转义；对分隔符、编码、表头采取可解释默认值，并为后续设置预留扩展。
- Office OpenXML 实质为 ZIP 容器：设置提取大小/解压比例上限，防止超大或异常容器消耗失控。
- PDF：按页处理，保留页码与原始块的关系；提取顺序可能与视觉阅读顺序不同，不用页内位置猜测虚假的行号。

## 5. 搜索方案对比：直接扫描、缓存、全文索引

| 方案 | 优点 | 缺点 | 适用情境 | 建议 |
|---|---|---|---|---|
| **A. 每次直接扫描解析文件** | 最简单；结果总是基于当前可读文件；无索引一致性问题；便于验证准确性 | 文件多、Office/PDF 体积大时重复解析慢 | 初版、规模未测清、准确性优先 | **v0.1～v1.0 默认基线** |
| **B. 提取文本缓存（SQLite/文件缓存）** | 重复搜索避免二次解析，改善 Office/PDF 搜索速度 | 缓存占空间且可能含敏感原文；修改/删除/设置变化需失效 | 重复搜同一批资料、解析耗时占主导 | **阶段 4 测量后增加** |
| **C. SQLite FTS5 索引** | 本机数据库、便于维护，全文查询可快很多 | 中文短词、连续子串、位置与查询逻辑需要额外设计；索引更新复杂 | 文件多、重复搜索频繁 | **P1**，需先通过正确性试验 |
| **D. Lucene.NET** | 更完整的倒排索引与分析器机制，查询能力强 | 部署、维护、分词器调校与索引一致性成本更高 | 数据量更大，复杂高级查询较多 | **后续评估** |
| **E. 自建双字 n-gram 候选索引** | 对“西瓜”类中文短词可优化候选筛选；实现语义可控 | 索引体积与更新成本；单字查询仍需另外处理 | 需要精确的中文子串检索且 FTS 不满足 | **实验选项** |

### 5.1 中文检索正确性：必须设“基线裁判”

例如输入“西瓜”，用户期望匹配 `今年买了西瓜汁`，与是否能通过词典分成某个完整词无关。**这是一种连续子串匹配需求。**

SQLite FTS5 自带的 `trigram` tokenization 按连续 **3 个 Unicode 字符**生成 token；官方文档说明通过全文 `MATCH` 查找**少于 3 字符**的子串不会匹配任何行。因此**不能直接用 FTS5 trigram MATCH 替代“西瓜”查询**。一些 `LIKE/GLOB` 情形也不会使用索引优化；不要假定换语法就能解决。详见文末 SQLite 文档。

推荐原则：
1. **正确性基线**：直接扫描解码/提取后的每个可搜索片段，使用确定的 Unicode 字面量子串匹配。
2. **未来索引只筛选候选**：先找到可能相关的文件/片段，再用同一个字面量匹配器复核，保证不误报。
3. **1/2/3 字中文、英文大小写、标点、跨块边界、组合词 AND/OR** 都须进入回归测试；不允许用索引后默默漏掉 1～2 字关键词。
4. **归一化规则显式可测**：可以选 NFC 与大小写不敏感比较，但要保留源文本位置映射。避免在用户不知情时使用会改变含义的激进 NFKC 转换。
5. **AND/OR 发生在文件级**：每个文件只保留其是否包含全部/任一词的判断；所有匹配项仍分别展示，不能把两个来自不同单元格的词组合成一段虚构上下文。

### 5.2 自适应路线不必一开始就造复杂系统

阶段 1：目录流式遍历 → 根据扩展名提取片段 → 字面量匹配 → 流式返回匹配文件/片段。阶段 4 记录**文件数、总体积、格式组成、冷/热时间、峰值内存、失败率**。若重复解析明显占时间，再优先加入“可失效提取缓存”；如果匹配本身成为瓶颈，再考虑索引。

如果未来支持策略切换，使用 `ISearchProvider` 接口（`DirectScanProvider`、`CachedScanProvider`、`IndexedProvider`），而不是在 UI 里到处添加“文件数 > 5000 则改算法”的规则。**阈值需要用硬件与真实数据量基准确定**，不可只按文件数量判断，因为一个超大 PDF 可能比上千 TXT 难处理。

### 5.3 缓存的失效与隐私

缓存键应至少考虑绝对路径、大小、最后修改时间、提取器版本与解析设置指纹；对高可靠场景可加内容哈希或按需复核。删除、移动、权限变化、文件修改以及选择是否搜索隐藏工作表等设置变化，都可能使旧条目失效。全文缓存等于在硬盘额外保留敏感文字，必须说明存储位置、清理入口和关闭方式，默认不将正文上传云端。

## 6. 精确定位：分级能力模型，而不是一次性“全格式必达”

| 格式 | 推荐定位数据 | 优先打开方式 | 可验证的回退 |
|---|---|---|---|
| TXT/MD/LOG | 文件路径 + 行号 + 列偏移 | 可配置编辑器支持行号参数时跳转 | 默认关联程序打开、提示行号 |
| CSV | 逻辑记录号 + 列号 + 可能的物理行 | 若有配置的编辑器则定位行 | 打开文件 + 提示记录/列 |
| XLSX | 工作表名称/标识 + A1 单元格地址 | 用户已安装 Office 时尝试 Excel COM 选择工作表/单元格 | 打开文件 + 复制/展示坐标 |
| PPTX | 幻灯片标识/序号 + 对象标识 | PowerPoint COM 尽量切换到幻灯片 | 打开文件 + 提示第 N 页 |
| DOCX | 段落/表格路径 + 精确文字范围候选 | Word COM 按可复现的范围定位 | 打开文件 + 展示段落与上下文 |
| PDF | 页码 + 可选页面矩形区域 | 有支持参数的阅读器则传页码 | 打开 PDF + 复制/提示页码 |

### 6.1 Office COM 的架构约束

- COM 对象只由**明确的用户动作**（双击匹配）驱动；不用于搜索时批量打开文件。
- 必须在恰当的 STA 线程环境中访问 Office 自动化对象；处理 Office 当前未启动/已打开文档、受保护视图、提示对话框、文件锁与超时。
- 避免对原文档进行保存、写入、更改宏设置。关闭/释放 COM 对象时不要误关用户原有的 Office 窗口。
- 对于 DOCX，提取的段落路径和 Office 打开的实际 Word Range 不一定一一对应；利用文档结构索引、上下文/全文查找做定位时，须考虑多次相同文本、修订、表格和不同版本。
- “定位成功”必须以对象/位置可核实为准；仅 `Process.Start` 打开文件只能算“打开成功”。

建议 `LocateResult` 明确区分：`Exact`（如 Excel B15 已选中）、`Section`（已导航到第8张幻灯片）、`OpenedOnly`（仅打开）、`Failed`。这能避免误导用户，并为将来增加其他 Office 套件/阅读器适配留下空间。

## 7. 项目目录与模块建议（以 .NET 为例）

```text
src/
├── LocalDocSearch.Desktop/          # WPF 或 Avalonia 的实际宿主
├── LocalDocSearch.Application/      # 搜索流程、设置协调、状态事件

├── LocalDocSearch.Search/           # 字面量匹配与未来可插拔 Provider
├── LocalDocSearch.Locators.Windows/ # Shell / 编辑器 / Office COM
└── LocalDocSearch.Infrastructure/   # 文件系统、配置、日志和可选缓存

tests/
├── LocalDocSearch.UnitTests/
├── LocalDocSearch.IntegrationTests/
├── LocalDocSearch.UiSmokeTests/
└── fixtures/
```

不要在第一天就生造许多空项目。可以先 `Desktop / Core / Tests` 三个项目做穿透原型，直到功能复杂度增长再按模块拆分；原则是**接口边界清晰，但不为了分层而分层**。

## 8. 质量保障与测试方法

### 8.1 单元测试

覆盖字面量匹配、AND/OR、匹配计数、重叠高亮、中文短词、空关键词、行号/单元格/段落位置映射、取消、编码异常及跨块边界。可考虑 xUnit/NUnit（引入时核对许可）。

### 8.2 集成测试

用**公开可再分发的原创样本**覆盖 DOCX、XLSX、PPTX、PDF、CSV。每个样本定义真实命中词、位置与数量；测试 `西瓜`、`苹果`、`西瓜 AND 苹果`、`西瓜 OR 苹果` 以及某个搜索范围开关。

### 8.3 Office 定位手工/自动辅助验证

在安装 Office 的 Windows 11 环境中验证 XLSX B15、PPT 第8页、DOCX 指定段落；再在**未安装 Office** 的干净虚拟机环境验证内容提取与回退。每个定位动作保留可观测结果，不以“窗口弹出”代替成功判断。

### 8.4 性能基线而非虚假性能承诺

建议设计三组固定数据集：小规模（数百文件）、中规模（数千文件）、大规模（数万混合文件或同等字节量），记录机器 CPU/内存/SSD、总字节量、冷搜索/热搜索时间、峰值内存、首结果延迟、失败数；对大 LOG、复杂 PDF、巨大 Excel 单独压力测试。实际阈值在结果出现后批准。

## 9. 构建、发布与开源许可证

### 9.1 项目许可证候选

| 许可证 | 优势 | 限制/义务 | 当前建议 |
|---|---|---|---|
| **MIT** | 简洁、使用与贡献门槛低，通常方便引入宽松许可依赖 | 没有 Apache-2.0 那样明确的专利授权文本；仍要保留版权和许可声明 | **优先候选** |
| **Apache-2.0** | 明确专利许可和相关终止条款，适合多人协作 | NOTICE/保留声明等合规操作较繁琐 | **并列值得考虑** |
| **GPL-3.0** | 对衍生作品的源代码开放要求更强 | 与其他依赖/分发安排的兼容性限制更高 | 若特别希望保护衍生开源再考虑 |

完全开源不等于必须 GPL；若采用 MIT 自研实现，也可以合法发布类似于 dnGrep 的功能。**不要从 GPL-3.0 的 dnGrep 直接复制代码，除非愿意遵守对应许可证对整体分发的要求。** 用第三方 SDK 必须检查当前具体版本的完整依赖树，而不仅看顶层项目仓库许可证。发布时明确标注 `THIRD-PARTY-NOTICES` 或等效文件。

建议首发 GitHub 仓库包含：`LICENSE`、`README.md`、`CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`（可选）、`SECURITY.md`、`CHANGELOG.md`、源码、测试、构建脚本和 Release 校验值。中文 README 首发，后续可加英文版。源码和二进制发布的许可声明需一致。

### 9.2 Windows 构建产物选择

| 分发方式 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **可解压 ZIP / portable** | 无需安装程序、便于测试和开发者使用 | 文件关联与自动升级体验弱 | **v1.0 提供** |
| **独立 EXE/安装程序** | 大众用户使用方便，安装卸载清晰 | 签名、SmartScreen 信誉、卸载和更新机制需管理 | **v1.0 提供** |
| **MSIX** | Windows 打包、卸载/系统集成规范 | 包身份、证书、发布渠道及某些应用集成限制需测试 | 作为候选，不先定 |
| **框架依赖式 .NET 发布** | 包体较小 | 用户需安装正确 .NET Desktop Runtime | 开发/小众测试版本可用 |
| **自包含式 .NET 发布** | 目标机器无需预先装对应 .NET 运行时 | 分发体积更大，需要跟进安全更新 | 公共发行版优先评估 |

开源项目早期可能没有受广泛信任的代码签名证书；应明确告知用户软件签名状态，提供校验和与构建说明，**不要引导用户无条件关闭安全功能**。GitHub Actions 可在 `windows-latest` 跑构建和测试，正式标签触发 Release；依赖固定版本并做好供应链审查。

## 10. 开发阶段建议的技术决策清单

| 决策号 | 问题 | 推荐的比较试验 | 决定时间点 |
|---|---|---|---|
| ADR-001 | WPF 还是 Avalonia？ | 同一 UI 原型：高亮、1万项列表、Office 开文件、高 DPI | 编写完整主界面前 |
| ADR-002 | XLSX 用 Open XML 还是 ClosedXML？ | 同一大/小工作簿对比提取正确性、内存和耗时 | 全格式提取前 |
| ADR-003 | Excel 公式/缓存值如何搜索？ | 带公式、格式、隐藏工作表的原创测试集 | 搜索范围设置定稿前 |
| ADR-004 | 直接扫描是否足够？ | 冷/热扫描与解析耗时报告 | 规划缓存/索引前 |
| ADR-005 | Office COM 各格式定位级别？ | 真实 Office，重复文字/隐藏工作表/已打开文档 | 双击定位承诺前 |
| ADR-006 | MIT 还是 Apache-2.0？ | 已引入依赖的许可与版权审计 | 仓库正式公开/首发前 |
| ADR-007 | 安装包与运行时策略？ | 干净 Win11 安装 + 更新卸载测试 | v1.0 候选发布前 |

### 建议最先做的 3 个实验

1. **C# GUI 原型**：WPF 与 Avalonia 分别实现“目录 + 搜索 + 分组高亮结果”，检查交互是否满足预期。
2. **跨格式解析样本**：同一词“西瓜”放入 8 类文件，确认提取内容、出处和上下文能否统一表示。
3. **Office 定位验证**：从 `Sheet2!B15`、PPT 第8页、Word 指定段落出发，测量 COM 能定位到哪一级；与无 Office 环境的回退对照。

完成后才正式批准技术栈与 v1.0 的精确定位能力表。

## 11. 风险及对应策略

| 风险 | 影响 | 处理 |
|---|---|---|
| 误把中文分词搜索当成精确子串搜索 | 漏报“西瓜”等短词 | 原文子串匹配为基准；索引候选必须复核 |
| Office 格式的视觉位置与底层 XML 不一致 | 精确定位失败 | 对各格式分级定位与真实回退；不伪报成功 |
| Excel “显示值”与原始值/公式不一致 | 用户误判漏搜 | 暴露语义与选项，明确缓存值限制 |
| 大量文件解析导致 CPU/内存过高 | UI 卡顿、崩溃 | 异步管线、限并发、流式处理、结果虚拟化 |
| 解析恶意/畸形文件 | 资源耗尽或异常 | ZIP/解压大小限制、超时/取消、错误隔离 |
| 索引/缓存内容过时 | 误报漏报 | 版本化缓存键、变更检测、必要时原文件复核 |
| 开源依赖许可证不兼容 | 发布法律风险 | 依赖 BOM、许可清单、避免复制不兼容项目代码 |
| 日志或缓存包含私密正文 | 隐私风险 | 最小化日志、默认无全文缓存、清理入口 |
| 从 Windows 迁到其他系统 | 重写定位与 UI | 业务核心不依赖 UI、Windows 适配器隔离 |

## 13. 需要一起做的最终技术选择

在不改变已经确认的产品需求前提下，我建议**优先讨论以下四点**：

1. **WPF vs Avalonia**：你更重视第一版 Windows 开发效率，还是未来跨平台成本？（我现阶段推荐 WPF。）
2. **Excel 提取**：是否更愿意先用较易上手的 ClosedXML 快速做通，还是直接用更可控的 Open XML SDK 兼顾大文件？（我倾向 Open XML SDK 优先，必要时混用。）
3. **搜索性能**：是否接受“v1.0 正确的直接扫描 + 性能测试，根据结果决定缓存”的路线？（我推荐接受。）
4. **项目许可证**：MIT 与 Apache-2.0 哪种符合你希望其他人使用、修改、再发布的方式？（目前偏 MIT；最终要完成依赖审查。）

**技术栈未定不是阻碍**。只要先验证数据提取和源位置，后续无论使用 WPF 还是 Avalonia，核心搜索能力都能够复用。
