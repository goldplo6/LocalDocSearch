# 多关键词候选预筛：可行性与实施计划

日期：2026-11-14。状态：已完成；1453 项完整回归、15 场景交替对照、rc.9 七种原生查询及只读预览通过，结果见[验收报告](literal-prefilter-results.md)。本轮依据[搜索实现原理](search-principles-and-next-steps.md)、[受限并发实验](bounded-concurrency-results.md)、[多文件效率](multifile-search-results.md)及现有引擎代码筛选改动，不把讨论中的方向当成已经测得的收益。

## 可行性判断

| 方向 | 判断 | 本轮处理 |
|---|---|---|
| 多词合并枚举所有命中 | 有潜力，但需要精确复现同词非重叠、跨词独立重叠、大小写、排序及预算触发顺序 | 先用任一词预筛减少确定无命中的扫描，命中枚举保留原逻辑 |
| 延后构造上下文 | 仅延后对象有收益空间；直接保存原文到 EOF 会使稀疏命中的大段长期滞留，当前结果字符预算不覆盖这些整段原文 | 本轮不引入原文滞留或第二轮提取；保留未来紧凑、受预算限制的存储方案 |
| 把 2／4 并发设为默认 | 现有多文件实窗有收益，但小文件 CPU 增加、单大文件无稳定收益，多份大型 Office/PDF 内存证据不足 | 默认仍为 1，原有显式实验入口继续保留 |
| 提取缓存／增量索引 | 对反复搜索可能有效，但需新增失效、清理、磁盘和中文子串语义契约；用户场景不固定 | 本轮保持每次重读源文件 |

## 选定实现

- 使用 .NET 10 已有的 `SearchValues<string>`，不增加 NuGet 依赖。每次查询在词表去重后创建一次、供本轮工作者只读共享。
- 至少 32 个不同关键词且当前片段至少 256 个 UTF-16 字符时，按现有 `Ordinal`／`OrdinalIgnoreCase` 比较模式求任一词最早位置。
- 返回 -1 只表示**当前片段**无任何词，跳过其逐词循环；其余情况从最早候选位置开始原逐词 `IndexOf`。不据此短路整文件 AND／OR，不改公式、不合并段落。
- 单词、少词、短片段与正则保留原匹配路径。初版 4 词门槛在少词场景回退；补测后采用 32 词门槛，正负结果均保留。
- 保留完整 EOF、来源元数据复核、警告、匹配及字符预算的检查顺序，完整文件才发布。只缩短在原文中的搜索，不延长任何片段原文的生命期。

## 验证与交付

1. 用独立的原始 `IndexOf` 参考枚举核对全部匹配字段，覆盖词前缀、重叠、中文、Unicode 大小写、代理对、边界长度、跨段公式和 1／2／4 并发。
2. 回归无候选后仍继续读取的晚错误／警告、预算超限、取消暂停及整文件原子发布。
3. 隔离快照 locked restore、完整解决方案构建及六套测试；不占用已有成品目录。
4. 用同一基准驱动分别加载本轮前后的 Core 程序集，交替 old→new→new→old，每组独立进程、三轮，至少覆盖 4／16／64 词无命中、稀疏及密集命中、单词、短片段和正则对照。完整结果摘要在独立验证轮计算，排除在性能耗时与累计分配之外。
5. 分别报告耗时、CPU、累计分配与进程寿命工作集高水位，保留变慢的场景；不把暖缓存说成冷缓存、不把累计分配当成峰值内存。
6. 整理新报告及可运行的本地构建，不自动 commit／push。当前成品与备份均留在工作区内，不重新创建 C 盘根目录成品。
