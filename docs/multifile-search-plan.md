# 多文件效率与搜索控制计划

日期：2026-11-13。状态：已完成。基线为 rc.7（982 项回归）；rc.8 完成小文件自适应缓冲与暂停、继续、停止，1173 项回归、独立解压实窗及浅目录交付通过。小文件交替基准累计分配下降约 82.4%；速度变化和变慢样本分别保留，不据此宣称普遍加速。实现、测量和验收见[结果报告](multifile-search-results.md)。

## 时间与空间权衡

- 总内存包括已保留完整结果、64 个待交付文件结果和 256 条问题队列、当前文件的结果与解析器、界面对象。分页只限制匹配行包装和可视控件，并不丢弃完整结果。
- 单文件结果字符串预算在分配前检查；全局结果字符预算在完整文件发布前检查。两者不是进程 RSS 上限；第三方 Office/PDF 解析仍可能先分配后返回。
- 更大的读取缓冲可减少大文件读取次数，但对大量几十字节的小文件，固定 16 KiB 级字节／字符缓冲会增加累计分配和 GC 工作。先让缓冲随文件规模有界变化，保持大文件块尺度与严格解码。
- 并发搜索可以重叠等待，却会增加同时存活的解析器、未提交文件结果和排序缓冲。当前文件原子发布、DFS 顺序及首结果取消均为既有契约；本轮优先消除单文件固定开销，不引入无界任务、全文缓存或索引。

## 先进实现的借鉴与边界

1. [.NET StreamReader 源码（v10.0.0）](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/IO/StreamReader.cs)：默认 reader 缓冲为 1 KiB、FileStream 缓冲为 4 KiB，源码注释明确解释较小数组对读取许多小文件的构造成本优势。借鉴分配尺度，不把运行时默认值当作所有语料的最优值。
2. [ripgrep 项目](https://github.com/BurntSushi/ripgrep)：递归搜索使用并行目录遍历、自动 Unicode 编码处理以及多种有界读取策略。其主要目标是文本行搜索；本项目还需完整 Office/PDF 提取、文件级公式判断、来源核验，不能直接把其耗时作为本产品基线。
3. [.NET Channels](https://learn.microsoft.com/en-us/dotnet/core/extensions/channels)：有界 Wait 模式让生产者等待容量，避免以无限排队换吞吐。本项目保留现有背压，不以丢弃完整结果换速度。
4. [.NET cooperative cancellation](https://learn.microsoft.com/en-us/dotnet/standard/threading/cancellation-in-managed-threads)：停止由令牌在检查点协作完成；暂停使用异步门闩，不挂起操作系统线程，不忙等。

## 实施范围

- 文本读取：小文件自适应缓冲；保持 BOM、严格 UTF、GB18030 预验证回退、CR/LF/CRLF、UTF-16 位置、完整 EOF、资源预算及只读属性。
- Core：每轮可选 SearchExecutionControl；在目录、文件、提取片段和结果交付边界检查暂停。请求暂停与已进入暂停等待明确区分，恢复继续原轮，取消可解除暂停等待。
- Desktop：搜索行增加暂停／继续和停止；保留 CancelSearchCommand 兼容。暂停请求期间排空已经接收的完整结果，再显示“已暂停”；停止保留已展示的完整文件，结束后可重新搜索。
- 保持现有结果区比例、双层虚拟化、分组和正则、预览及原文件操作。本轮不继续调试原文件自动填词，不新增依赖。

## 验证与交付

- 新增确定性核心与界面控制测试、文本缓冲边界测试；原功能与资源断言保持，旧状态文案断言由“已取消”同步为“已停止”。
- 相同原创语料的 many-small、large-log、mixed、dense-file、global-budget 前后各三轮；必要时交替复测。记录耗时、首结果、累计分配和进程寿命峰值，保留变慢场景；未清 OS 缓存，不称冷缓存。
